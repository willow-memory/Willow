# Kept: this repository asked what it remembers

One stack, built by hand on 2026-11-11, over one folder: this repository
as it was at commit `82983e8`, the last before this folder existed.
It came out of a conversation about supercomputing that ended on a claim:
the big machines recompute what should be remembered, and computing should
be shared. The stack asks what willow already does toward that, and tries
the idea on one real computation. Nothing here was generated by a model;
every line below is what a step printed, or a count of it.

**Whose wants these are.** A stack is a row of wants in the person's own
words ([stacks, for agents](../../docs/agents/stacks.md)). Here the person
gave the subject ("remembering over recomputing, and shared computing") and
said to add whatever might come up, at least thirteen. So the 31 wants in
[stack.md](stack.md) are the session's, each written above its step, and
they stand as proposals: cut any of them. The Forge could not run
(`forge-play` is not installed), so each step was written by hand, added
one at a time, and the stack run from a fresh box after each.

## What is here

- [stack.md](stack.md): 33 steps of 28 add-ons in ten pools, for
  [stack](../../adapters/stdlib/stack/). Paths of the machine it ran on
  are `<scratch>`, `<pile>` for the folder it asks and `<repo>` for this
  checkout.
- [words.txt](words.txt): the six-line words list the box carried, written
  from what the questions missed and cut once.
- [questions.txt](questions.txt): the sixteen questions scan was asked.
- [results/](results/): the last run's log, a line as each step started
  and ended, and what glance said of the 48 answers.
- [rebuild.sh](rebuild.sh): `bash demo/kept/rebuild.sh SCRATCH` clones
  the repository at the pinned commit into SCRATCH, makes a fresh box over
  that clone, puts the words list on it, runs the stack and verifies the
  record. It takes about three and a half minutes, two and a half of
  them the last step.

## The pile is pinned, so the stack can't find itself

The first runs asked this checkout. Then this folder was committed into
it, and the stack began answering from its own write-up: the claim check
closed on [stack.md](stack.md), where the claim is written; glance counted
25 questions held whole, up from 16, by finding
[questions.txt](questions.txt); and five of the seven passages one step
served were this report or the commits that added it. Asked about floating
point, it quoted the line below that says nothing here speaks of it.

A pile that holds what was asked of it, and what was said of the answers,
agrees with itself. So the pile is no longer this checkout. `rebuild.sh`
clones the repository at one named commit, `82983e8`, into scratch, and the
box, the readers and every index are over that clone. It holds 1,022
commits and no trace of this folder. Run that way, the stack gives the
numbers of the first run again, to the line.

Two things came with it. The folder asked is now named: a commit is a name
for exactly these bytes, so someone else's run is of the same pile. And the
run no longer dirties what it reads: add-ons run from this checkout, so
Python's `.pyc` files land here and not in the pile, and box-health's count
of files it can't read fell from 11 to 1.

`rebuild.sh SCRATCH COMMIT` asks another commit. From `b4a8223` on, it
finds itself again.

## What held

- **Read once, kept, and known to be current.** index-cache and pile-store
  hash each file and rebuild only when one changed. From the second run on,
  all four said `current`, and 48 questions took three seconds.
- **A name from the bytes alone.** ids gave `kernel.py` the name git gives
  it, with nothing sent anywhere. Two people holding the same file can find
  that out by comparing a line.
- **A computation done twice was the same.** The simulation's two runs
  came out byte for byte the same, so the second bought nothing. That is
  the claim in small: had the first run been kept under a name made from
  its inputs, the second need not have run.
- **The words list did its job once cut.** The first list had eleven
  lines and closed three empty answers, but `core = cores` and
  `supercomputer = cores` together served the constitution's "the core
  reaches nothing". Cut to six lines, "a supercomputer queue" lands on
  how CI splits tests by their past seconds, which is the nearest thing
  here to a scheduler.

## What didn't

- **The record remembers almost none of this.** After 28 steps it holds
  two rows: the start, and fixity's. The 48 answers, the claim checks and
  the simulation are in the run's folder, not on the chain, so prov had
  nothing to say of them and the Merkle root covers none of them. What a
  stack found is kept as files; only what an add-on appends is provable.
- **The same work gives a different record each time.** Rows carry the
  time and a fresh box has a fresh key, so the root differs run to run
  though every step printed the same. The outputs can be named by their
  bytes; the record of making them cannot be compared that way.
- **No one place holds the idea.** claim-check found nothing that has
  "named by its inputs", "kept" and "shared" together. The parts are here
  apart: ids names, index-cache and ci-memo keep, share and secure-sum
  send. Nothing joins them into a result anyone can look up before
  computing it.
- **Sharing waits on a seal, by design.** wasm, wasi-python, kart,
  secure-sum and share run only what the person sealed, so none of them
  is a step here. This stack shows a result is worth keeping; whether to
  send one is the person's to decide, with their key.
- **Same bytes was shown on one machine only.** Two runs with one Python
  and one numpy say nothing of another machine. The card for wasm makes
  that promise by fixing the runtime's bytes; this stack did not test it.
- **`float` found nothing.** No file here speaks of floating point
  results differing between machines. That is the honest answer, and the
  open problem the conversation ended on.

## Since: run again, against the real project

The simulation steps above ran star-system's stand-in checkout. Later the
same day the stack was run again with steps 18 and 19 pointed at the real
science_bitch, at its commit `2fae2f2` of 10 November, after two things on
this side were brought up to it:

- **The page names the checkout's own method.** Row 18's fault is fixed:
  the stand-in is now called `fixed-velocity-verlet-stand-in`, and
  "Yoshida" is said only of a checkout whose own name says so.
- **The page carries the project's own name for the setup.** The project
  now gives every setup a SHA-256 digest of its inputs. star-system reads
  it off the checkout and writes it as a line, only when that setup builds,
  bit for bit, the system it ran.

What that run said, on the pinned pile, before step 29 was added: 28 steps
in 83 seconds, the same 5 flagged. The two real runs
were the same, byte for byte; energy drifted 6.7e-14 over three orbits of
Jupiter, against the stand-in's 7.2e-11; and both pages carry the setup
digest `sha256:dd4c9ad5…`, the one the project's own function gives.

That digest is the piece "What didn't" says nothing here joins: a result
named by its inputs. It is the project's, not willow's, and it is now on a
page a box can hold.

## Since: what the steps take from one another

The stack is written as a row and run as one. Read by the stack-bridges
add-on, it is not one. Of its 33 steps, 11 take nothing any other step
made. The 28 bridges between the rest go three steps deep at most, from
glance down through scan and an index to the reader that wrote its
folder.

So it could have run in four rounds: 11 steps at once, then 15, then 5,
then 2. It ran one step after another for about a minute, and two and a
half more for the last. That is the conversation's second half in small:
the work was shareable as written, and nothing in how it was run knew.

Twelve of those bridges are the record. Before the last step only fixity
adds a row to it, by its card, and every step that names the record after
it is placed after it. That errs toward waiting: a step may name the record and never read a
row.

## Since: the run on the record

"What didn't" says the record remembered two rows of 28 steps. The last
step is now the stack-row add-on, and the record ends with a third: the 32
steps before it, each with its place, its add-on, the stack's marks of how
it was asked, how it ended and the SHA-256 of what it printed. The six
that ended other than clean are there as that. No output is on the row and
no argument, since a question is the person's words.

So what this run found can be held to: a step's kept output either hashes
to what the row says or it doesn't. What it does not yet do is get used.
prov runs before the row is written, and writes what it wrote before.

## Since: what the folder says it needs, sifted

Asked what this folder needs from its owner, the record's own page says
25 dates are coming up in the next fortnight. Not one is the repository's.
A made-up electrician's contract falls due, a made-up bookkeeper's phone
bill, a boiler in an example.

The kinds add-on knows which files are tests, fixtures, made-up people's
and frozen, from what the repository already declares. Its `sift` takes a
report and leaves those rows out. The 25 become 11, and the 136
references that don't hold become 60.

What is left is where to look next, and it is two different things. Eight
of the 11 dates are in one demo's saved model runs, which nothing
declares: a hole in the kinds, and the sift shows it. The other three are
examples, on two cards and in one script's own description. A card is a
kind, and a true one; an example on it is not the card speaking. That is
a finer line than a file's kind can draw.

## The rule

The session proposed and never sealed. The box is a scratch one with a
scratch key that `init` made; nothing was approved, and nothing was written
into the repository but this folder. To use the stack, run it over a box
of your own and seal what you choose.

## Its test

[test_kept.py](test_kept.py) holds what is committed: the stack parses,
names only add-ons that are here and no machine of its own, every step
that reads the repository reads the pinned pile and never this checkout, a
step takes only an earlier step's output, the words list is one the kernel
reads, and the log is the stack's and holds nothing of this folder.
